## Diagnostics / erase workflow

### erase-partition.sh's pre-sanitize cross-check compared a drive serial against a machine serial — always a coincidental match at best
- **Symptom**: erase-partition.sh aborts at the "Cross-check against opening diagnostic" step with "no matching 'before' row", even though a before-diagnostic was clearly run and recorded for that machine (e.g. 001/CIAD7562).
- **Cause**: diagnostics.sh (v0.3, v0.4) records the **machine's chassis serial** (`dmidecode -t system`) in the `serial_number` column. erase-partition.sh's cross-check reads the **drive's own serial** (`nvme id-ctrl` / `smartctl -i`) and searched for it in that same `serial_number` column. These are two different numbers — the chassis serial identifies the machine, the drive serial identifies the physical disk, and a drive can in principle be swapped between chassis without the chassis serial changing. The match could only ever succeed if the two happened to be identical, which is not something to rely on.
- **Fix**: diagnostics.sh v0.5 adds a `drive_serial` column (16th field), populated the same way erase-partition.sh already reads it (`nvme id-ctrl`/`smartctl -i`). erase-partition.sh now cross-checks against `drive_serial`, scoped first by CIAD number, instead of against `serial_number`.
- **Consequence for machines already diagnosed under v0.3/v0.4**: their "before" row in `summary.csv` has no `drive_serial` value, so erase-partition.sh cannot cross-check against it — even with the fix. **Every such machine needs its "before" diagnostic re-run under diagnostics.sh v0.5 before erase-partition.sh will proceed on it.** erase-partition.sh v2 detects this specific case and tells you to re-run the before-stage rather than giving a generic "no match" error, so you don't need to guess which failure mode you hit.
- **Applies to**: Every machine diagnosed before this fix (v0.5/v2) landed — i.e. the whole batch run so far, not just 001/CIAD7562. Re-running the before-stage diagnostic is quick (a few minutes) and non-destructive, so this is a one-time tax on already-processed machines, not a redesign of the workflow.

### NVMe drive reports Format NVM + crypto-erase support that isn't actually implemented — no Purge-tier sanitization path exists on this drive
- **Symptom**: `nvme format --ses=2` (and `--ses=1`, `--ses=0`) all fail identically with `NVMe status: Invalid Command Opcode: A reserved coded value or an unsupported value in the command opcode field(0x2001)`, despite `nvme id-ctrl -H` reporting `oacs=0x17` (Format NVM supported) and `fna=0x4` (crypto erase supported). `sanicap=0` in the same output confirms the device-level Sanitize command (the other potential Purge-tier path) is also not implemented — there is no fallback sanitize mechanism to try instead.
- **Diagnosis trail** (in order, each step ruling out a different explanation):
  1. **Mount/swap check** (`lsblk`, `swapon --show`) — ruled out an active mount holding the device, which would produce a different NVMe status (namespace-attached), not this one.
  2. **SES sweep** (`--ses=0/1/2`, all with `--force`) — identical rejection across all three values. This rules out an SES-specific rejection (e.g. a locking mechanism gating only the secure-erase variants) — the controller is refusing the Format NVM opcode (`0x80`) itself, independent of which erase semantics were requested. Plain `--ses=0` (no crypto/security handshake at all) failing the same way also weakens the Opal-locking hypothesis, since a lock state wouldn't normally block a non-secure format.
  3. **`admin-passthru --opcode=0x80`** (bypassing nvme-cli's `format` subcommand entirely, with `--namespace-id` set explicitly to match `/dev/nvme0n1` — an initial attempt without it returned `Invalid Namespace or Format`, a different status code, because `admin-passthru` doesn't infer the namespace ID the way `nvme format` does) — same `Invalid Command Opcode` rejection. This rules out an nvme-cli bug in how it constructs the Format command; the controller itself is rejecting the opcode.
  4. **`dmesg | grep -iE "lock|secur|opal"`** — no locking-related kernel messages. Combined with #2, this closes the TCG Opal/BitLocker-eDrive-locking hypothesis (plausible a priori on a Lenovo ThinkCentre SFF fleet) as the explanation for this specific failure.
- **Cause**: firmware misreporting. This exact pattern — `oacs`/`fna` claiming Format NVM and crypto-erase support that the controller then rejects at the opcode level — is a documented issue on several client/OEM NVMe SSDs from this general era, independent of vendor-specific locking schemes. Confirmed here on a Samsung MZVLW256HEHP-000L7 (machine 001/CIAD7562).
- **Decision (2026-09-22, accepted exception — not a default)**: rather than pulling affected machines from the participant-redeployment pool, a Clear-tier (NIST SP 800-88) zero-fill overwrite via `nwipe` is accepted as the fallback sanitization method for NVMe drives confirmed to reject Format NVM at the opcode level. This is a deliberate, documented deviation from the Purge-tier method methodology.md §4 otherwise mandates — see methodology.md §4 for the compliance rationale and residual-risk statement, and methodology.md §4.2 for the underlying mechanism (why overwrite doesn't fully reach wear-leveled/over-provisioned flash).
- **Fix**: erase-partition.sh v3 detects this specific failure signature (`grep -qiE "invalid.?command.?opcode|INVALID_OPCODE"` against the Format NVM command's output) and falls back to `nwipe --autonuke --method=zero` automatically, recording the result under a distinct `erase_method` string (`"nwipe overwrite (Clear-tier fallback — Format NVM confirmed unsupported despite oacs/fna claiming support; see known-issues.md)"`) so it's never conflated with a Purge-tier crypto-erase result in `summary.csv`. Any Format NVM failure that does *not* match this specific signature (a mount lock, a transient error, a genuinely failing drive) still stops for manual investigation rather than falling back automatically.
- **Applies to**: confirmed on this one unit (Samsung MZVLW256HEHP-000L7, 001/CIAD7562) via the full diagnosis trail above. **Not yet confirmed model-wide** — firmware revision could in principle differ across units even within the same OEM SKU. If a second machine with this drive model turns up in the batch, spot-checking it with the same SES=0 test before fully trusting this as a model-wide (rather than unit-specific) finding is worth doing, though the fallback logic in erase-partition.sh v3 will catch and handle it correctly either way — it detects the failure per-machine, not by matching drive model.

### nwipe's default "blanking" pass silently doubled wipe time on every `--method=zero` run
- **Symptom**: a `nwipe --nogui` zero-fill on machine 001/CIAD7562 (256GB NVMe, Clear-tier fallback case) was still running well past the point a single pass over the drive's capacity should have completed. Tracking the live process's actual disk writes via `/proc/<pid>/io`'s `write_bytes` counter (two samples, `sudo cat /proc/<pid>/io` a fixed interval apart) showed cumulative bytes written already exceeding the drive's real capacity (confirmed with `sudo blockdev --getsize64 /dev/nvme0n1` — 256,060,514,304 bytes) and still climbing, well after a single pass should have finished.
- **Cause**: nwipe's default behavior is to run a final "blanking" pass after the selected wipe method's own pass, for every method *except* RCMP TSSIT OPS-II — `zero` is not exempt. Neither `nwipe` invocation in `erase-partition.sh` (NVMe Clear-tier fallback branch, plain HDD branch) passed `--noblank`, so both were silently running a full second all-zero pass on top of the first. For `--method=zero` specifically this second pass is pure redundancy — the method's own pass already leaves the drive all-zero, so blanking again verifies nothing new and changes nothing about the sanitization result.
- **Diagnosis note**: nwipe's own progress signaling (`SIGUSR1`, documented to log current wiping statistics) produced no visible output when sent to the process during this investigation, even after confirming the signal reached the correct worker PID (via the `sudo`→monitor→worker PID chain, `ps -eo pid,ppid,lstart,cmd`). The likely explanation is C stdio buffering: nwipe's stdout is piped through `tee` in `run_logged()` rather than attached to a real terminal, which typically switches glibc's stdio from line-buffered to fully-buffered output — but this wasn't confirmed against nwipe's source, so treat it as a plausible explanation, not a settled one. The `/proc/<pid>/io` byte-counting approach doesn't depend on nwipe's own output at all, which is why it caught this when the signal-based check didn't.
- **Fix**: `erase-partition.sh` v4 adds `--noblank` to both `nwipe` invocations. No change to verification logic — `readback-sample` verification only checks final on-disk state, unaffected by dropping the redundant pass. A manual progress-check comment block (the `/proc/<pid>/io` method above, plus the `pgrep`/`ps` steps to find the correct worker PID through sudo's monitor chain) was added to the script ahead of §5 instead of building automated in-script progress reporting — decided against the latter as added process-management complexity/fragility in a script that's already destructive by design, for a convenience feature.
- **Applies to**: every machine sanitized via either `nwipe` branch (NVMe Clear-tier fallback or plain HDD) before this fix landed — i.e. the whole batch run so far that hit either of those paths, not just 001/CIAD7562. Unlike the drive_serial issue above, this doesn't invalidate any prior result (the extra pass didn't harm anything, it just wasted time) — no re-run needed on already-processed machines, only faster runs going forward.

### `hdparm --security-erase-enhanced` fails erase-partition.sh's own verification on a real SATA SSD
- **Symptom**: on 002 (SATA SSD), `erase-partition.sh` v9's SATA-SSD branch ran `hdparm --security-erase-enhanced` to completion (`exit=0`), but the following `readback-sample` verification step then failed — non-zero data present at the offset-0% sample.
- **Cause**: per ATA spec, plain `SECURITY ERASE UNIT` is defined to write binary zeroes to user data areas; `ENHANCED SECURITY ERASE UNIT` writes a manufacturer-defined pattern instead, which is not guaranteed to be zero. `erase-partition.sh`'s `readback-sample` verification only checks sampled offsets against an all-zero reference (`cmp` against `/dev/zero`) — a design choice that was fine when the SATA-SSD branch used plain Secure Erase exclusively, but breaks the moment Enhanced is used on a drive whose vendor pattern isn't zero.
- **Confirmation**: re-running the identical drive (002) with the prior (v1-tagged) script — plain `--security-erase`, no Enhanced preference — passed verification cleanly at every sampled offset. Same drive, same verification method, only the erase variant changed.
- **Fix**: `erase-partition.sh` v10 reverts the SATA-SSD branch to plain `--security-erase` only; the Enhanced-preferring branch introduced in v9 is removed. See `methodology.md` §4.3 for the full reasoning, including why teaching the verification step to accept a non-zero pattern instead was considered and rejected (added complexity for a benefit — Enhanced's broader reallocated/spare-sector coverage — that isn't NIST-certified in the first place; see the same section).
- **Applies to**: any machine that would have hit the SATA-SSD branch between v9's introduction and v10's revert (2026-09-28, same day — narrow window, but worth checking `erase_method` in any affected machine's `summary.csv` row if that window is uncertain). Machines sanitized with v1–v8's plain `--security-erase`, or v10 onward, are unaffected.
