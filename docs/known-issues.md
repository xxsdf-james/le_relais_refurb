## Booting from USB

### ThinkCentre M900z doesn't list most USB sticks as boot devices — fixed by enabling USB Enumeration Delay
- **Symptom**: on 003 (ThinkCentre M900z), the BIOS didn't offer most USB sticks as boot devices. Four different sticks were tried in every USB port, with both Ubuntu and Windows 11 media, and only one stick was ever recognized. Every stick that failed on 003 had been tested as working in another machine.
- **Cause**: the BIOS checks the USB ports during startup before some sticks are ready to answer, so those sticks never appear in the boot list. That explains why it varied from stick to stick. The BIOS setting **USB Enumeration Delay** (Devices → USB Setup, off by default) gives USB devices extra time to be detected at startup. According to Lenovo's ThinkCentre BIOS reference, it "provides extra delay to USB enumeration to improve compatibility" and may increase POST time (<https://docs.lenovocdrt.com/ref/bios/settings/thinkcentre/usb_setup/>).
- **Fix**: enable USB Enumeration Delay in the BIOS (F1 at the Lenovo logo), save with F10, then boot the stick from the F12 menu. After this change 003 recognized more sticks and booted Ubuntu Live 26.04 (2026-09-30). The only cost is a slightly longer startup screen.
- **Not explained by this fix — watch for it**: before the setting was changed, the one recognized stick (freshly rewritten with Ubuntu) got as far as Ubuntu's boot menu and kernel. Ubuntu then stopped with "unable to find a medium containing a live file system". The machine then wouldn't power off and showed a kernel panic, and afterwards the BIOS stopped recognizing that stick too. This happened after Linux had taken over the USB ports, and the enumeration delay only affects the BIOS, so the setting doesn't account for it. Nothing has confirmed whether it was a temporary bad USB state on that machine or a flaky USB connection. If a live session on an M900z shows the stick dropping out, check with `sudo dmesg | grep -iE 'usb.*(reset|disconnect|error)'` before running diagnostics or a wipe. Repeated resets or disconnects on the stick mean it isn't safe to go on.
- **Boot mode on the same machine**: 003's BIOS allowed both boot modes, with the legacy (non-UEFI) entries first in the boot order, and Secure Boot was off (opening diagnostics, 2026-09-30). The opening diagnostics still booted via UEFI. A legacy Windows install would leave no Windows Boot Manager UEFI entry, so closing diagnostics could never mark the machine GREEN, and Secure Boot would stay off. Before installing Windows, set **CSM** to Disabled, **Boot Mode** to UEFI Only and **Secure Boot** to Enabled. Menu names haven't been checked on the M900z. Don't use F9 (load defaults) after enabling USB Enumeration Delay: it turns the delay back off.
- **Applies to**: confirmed on 003 only. If other M900z units are in the batch, enable the setting before their first boot attempt. It's harmless and fixed this machine, but nobody has checked whether every M900z needs it. 001 and 002 booted USB without it.

## Diagnostics / erase workflow

### erase-partition.sh's pre-sanitize cross-check compared a drive serial against a machine serial — always a coincidental match at best
- **Symptom**: erase-partition.sh aborts at the "Cross-check against opening diagnostic" step with "no matching 'before' row", even though a before-diagnostic was clearly run and recorded for that machine (e.g. 001/CIAD7562).
- **Cause**: diagnostics.sh (v0.3, v0.4) records the **machine's chassis serial** (`dmidecode -t system`) in the `serial_number` column. erase-partition.sh's cross-check reads the **drive's own serial** (`nvme id-ctrl` / `smartctl -i`) and searched for it in that same `serial_number` column. These are two different numbers — the chassis serial identifies the machine, the drive serial identifies the physical disk, and a drive can in principle be swapped between chassis without the chassis serial changing. The match could only ever succeed if the two happened to be identical, which is not something to rely on.
- **Fix**: diagnostics.sh v0.5 adds a `drive_serial` column (16th field), populated the same way erase-partition.sh already reads it (`nvme id-ctrl`/`smartctl -i`). erase-partition.sh now cross-checks against `drive_serial`, scoped first by CIAD number, instead of against `serial_number`.
- **Consequence for machines already diagnosed under v0.3/v0.4**: their "before" row in `summary.csv` has no `drive_serial` value, so erase-partition.sh cannot cross-check against it — even with the fix. **Every such machine needs its "before" diagnostic re-run under diagnostics.sh v0.5 before erase-partition.sh will proceed on it.** erase-partition.sh v2 detects this specific case and tells you to re-run the before-stage rather than giving a generic "no match" error, so you don't need to guess which failure mode you hit.
- **Applies to**: Every machine diagnosed before this fix (v0.5/v2) landed — i.e. the whole batch run so far, not just 001/CIAD7562. Re-running the before-stage diagnostic is quick (a few minutes) and non-destructive, so this is a one-time tax on already-processed machines, not a redesign of the workflow.

### NVMe drive rejects Format NVM at the opcode level — likely a BIOS lock cleared by suspend/resume, not missing firmware support (cause revised 2026-10-13)
- **Symptom**: `nvme format --ses=2` (and `--ses=1`, `--ses=0`) all fail identically with `NVMe status: Invalid Command Opcode: A reserved coded value or an unsupported value in the command opcode field(0x2001)`, despite `nvme id-ctrl -H` reporting `oacs=0x17` (Format NVM supported) and `fna=0x4` (crypto erase supported). `sanicap=0` in the same output confirms the device-level Sanitize command (the other potential Purge-tier path) is also not implemented — there is no fallback sanitize mechanism to try instead.
- **Diagnosis trail** (in order, each step ruling out a different explanation):
  1. **Mount/swap check** (`lsblk`, `swapon --show`) — ruled out an active mount holding the device, which would produce a different NVMe status (namespace-attached), not this one.
  2. **SES sweep** (`--ses=0/1/2`, all with `--force`) — identical rejection across all three values. This rules out an SES-specific rejection (e.g. a locking mechanism gating only the secure-erase variants) — the controller is refusing the Format NVM opcode (`0x80`) itself, independent of which erase semantics were requested. Plain `--ses=0` (no crypto/security handshake at all) failing the same way also weakens the Opal-locking hypothesis, since a lock state wouldn't normally block a non-secure format.
  3. **`admin-passthru --opcode=0x80`** (bypassing nvme-cli's `format` subcommand entirely, with `--namespace-id` set explicitly to match `/dev/nvme0n1` — an initial attempt without it returned `Invalid Namespace or Format`, a different status code, because `admin-passthru` doesn't infer the namespace ID the way `nvme format` does) — same `Invalid Command Opcode` rejection. This rules out an nvme-cli bug in how it constructs the Format command; the controller itself is rejecting the opcode.
  4. **`dmesg | grep -iE "lock|secur|opal"`** — no locking-related kernel messages. Combined with #2, this closes the TCG Opal/BitLocker-eDrive-locking hypothesis (plausible a priori on a Lenovo ThinkCentre SFF fleet) as the explanation for this specific failure.
- **Update (2026-10-13, 032/CIAD7498) — the cause below is probably wrong**: 032 has the same drive model *and* firmware (`5L7QCXB7`) as 001. After a suspend/resume (the SATA freeze-lock fix, methodology.md §4.3), `nvme format --ses=2` succeeded and the marker-file verification passed. So the controller does implement Format NVM; the likelier cause is a lock the BIOS sets at every POST and a resume clears without POST, the same pattern Thomas-Krenn documents for `INVALID_OPCODE(2001)` on a Samsung PM983 (<https://www.thomas-krenn.com/de/wiki/NVME_Admin_command_error_INVALID_OPCODE(2001)>). Diagnosis step 4 (no lock messages in `dmesg`) didn't rule this out. **Not yet confirmed**: 032 wasn't tried *without* a suspend first, so a per-unit difference isn't fully excluded. On the next machine with this drive, run without suspending, expect 0x2001, then suspend and re-run. erase-partition.sh v12 now stops on 0x2001 and asks for a suspend before falling back to nwipe.
  - Two side effects seen on 032, handled in v12: `sgdisk --zap-all` exited 2 because the crypto-erased GPT read back as garbage, although the zap worked (`sgdisk -p` and `lsblk` showed an empty disk); and sgdisk reported the **backup GPT header (last sector) as valid** after the erase, which a full crypto erase shouldn't allow. That one is unexplained (stale page cache, or the erase not reaching the end of the disk); v12 reads the last sector directly from the drive before the zap and fails verification if the GPT signature is still there.
  - **022/CIAD7448 (2026-10-13): suspend did not help on a different drive model.** 022 has a Samsung **MZVLB256HAHQ-000L7** (PM981, firmware `1L2QEXD7`), not the MZVLW (PM961) in 001 and 032. It was suspended and resumed, then re-run with v12 to try for a crypto erase, and still got 0x2001: the rejection survives a suspend on this drive. This doesn't contradict 032: the suspend fix is so far only seen on the PM961. For the PM981 the original explanation (no working Format NVM) may still be right, or it's locked in a way a suspend doesn't clear; unknown. The redo cost 022 its Windows install: v12 went straight to a second zero-fill, and the crypto-erase marker (1 MiB in, the start of the EFI partition) had already been written. v13 fixes both: the marker block is restored on any refused format, and the nwipe fallback asks first (default No).
  - **Still to test:** 001/CIAD7562, which has the same PM961 drive as 032, with v13: fresh boot, expect 0x2001 and the suspend stop, then suspend and re-run.
- **Cause (original, 2026-09-22 — superseded by the update above)**: firmware misreporting. This exact pattern — `oacs`/`fna` claiming Format NVM and crypto-erase support that the controller then rejects at the opcode level — is a documented issue on several client/OEM NVMe SSDs from this general era, independent of vendor-specific locking schemes. Confirmed here on a Samsung MZVLW256HEHP-000L7 (machine 001/CIAD7562).
- **Decision (2026-09-22, accepted exception — not a default)**: rather than pulling affected machines from the participant-redeployment pool, a Clear-tier (NIST SP 800-88) zero-fill overwrite via `nwipe` is accepted as the fallback sanitization method for NVMe drives confirmed to reject Format NVM at the opcode level. This is a deliberate, documented deviation from the Purge-tier method methodology.md §4 otherwise mandates — see methodology.md §4 for the compliance rationale and residual-risk statement, and methodology.md §4.2 for the underlying mechanism (why overwrite doesn't fully reach wear-leveled/over-provisioned flash).
- **Fix**: erase-partition.sh v3 detects this specific failure signature (`grep -qiE "invalid.?command.?opcode|INVALID_OPCODE"` against the Format NVM command's output) and falls back to `nwipe --autonuke --method=zero` automatically, recording the result under a distinct `erase_method` string (`"nwipe overwrite (Clear-tier fallback — Format NVM confirmed unsupported despite oacs/fna claiming support; see known-issues.md)"`) so it's never conflated with a Purge-tier crypto-erase result in `summary.csv`. Any Format NVM failure that does *not* match this specific signature (a mount lock, a transient error, a genuinely failing drive) still stops for manual investigation rather than falling back automatically.
- **Applies to**: confirmed on this one unit (Samsung MZVLW256HEHP-000L7, 001/CIAD7562) via the full diagnosis trail above. **Not yet confirmed model-wide** — firmware revision could in principle differ across units even within the same OEM SKU. If a second machine with this drive model turns up in the batch, spot-checking it with the same SES=0 test before fully trusting this as a model-wide (rather than unit-specific) finding is worth doing, though the fallback logic in erase-partition.sh v3 will catch and handle it correctly either way — it detects the failure per-machine, not by matching drive model.

### nwipe's default "blanking" pass silently doubled wipe time on every `--method=zero` run
- **Symptom**: a `nwipe --nogui` zero-fill on machine 001/CIAD7562 (256GB NVMe, Clear-tier fallback case) was still running well past the point a single pass over the drive's capacity should have completed. Tracking the live process's actual disk writes via `/proc/<pid>/io`'s `write_bytes` counter (two samples, `sudo cat /proc/<pid>/io` a fixed interval apart) showed cumulative bytes written already exceeding the drive's real capacity (confirmed with `sudo blockdev --getsize64 /dev/nvme0n1` — 256,060,514,304 bytes) and still climbing, well after a single pass should have finished.
- **Cause**: nwipe's default behavior is to run a final "blanking" pass after the selected wipe method's own pass, for every method *except* RCMP TSSIT OPS-II — `zero` is not exempt. Neither `nwipe` invocation in `erase-partition.sh` (NVMe Clear-tier fallback branch, plain HDD branch) passed `--noblank`, so both were silently running a full second all-zero pass on top of the first. For `--method=zero` specifically this second pass is pure redundancy — the method's own pass already leaves the drive all-zero, so blanking again verifies nothing new and changes nothing about the sanitization result.
- **Diagnosis note**: nwipe's own progress signaling (`SIGUSR1`, documented to log current wiping statistics) produced no visible output when sent to the process during this investigation, even after confirming the signal reached the correct worker PID (via the `sudo`→monitor→worker PID chain, `ps -eo pid,ppid,lstart,cmd`). The likely explanation is C stdio buffering: nwipe's stdout is piped through `tee` in `run_logged()` rather than attached to a real terminal, which typically switches glibc's stdio from line-buffered to fully-buffered output — but this wasn't confirmed against nwipe's source, so treat it as a plausible explanation, not a settled one. The `/proc/<pid>/io` byte-counting approach doesn't depend on nwipe's own output at all, which is why it caught this when the signal-based check didn't.
- **Fix**: `erase-partition.sh` v4 adds `--noblank` to both `nwipe` invocations. No change to verification logic — `readback-sample` verification only checks final on-disk state, unaffected by dropping the redundant pass. A manual progress-check comment block (the `/proc/<pid>/io` method above, plus the `pgrep`/`ps` steps to find the correct worker PID through sudo's monitor chain) was added to the script ahead of §5 instead of building automated in-script progress reporting — decided against the latter as added process-management complexity/fragility in a script that's already destructive by design, for a convenience feature.
- **Applies to**: every machine sanitized via either `nwipe` branch (NVMe Clear-tier fallback or plain HDD) before this fix landed — i.e. the whole batch run so far that hit either of those paths, not just 001/CIAD7562. Unlike the drive_serial issue above, this doesn't invalidate any prior result (the extra pass didn't harm anything, it just wasted time) — no re-run needed on already-processed machines, only faster runs going forward.

### nwipe looks hung for over an hour after "bytes written" — it's reading the drive back
- **Symptom**: on 040/FR1586 (HP EliteOne 800 G1, 500 GB HGST HDD, 2026-10-19), the log stopped at `500107862016 bytes written to /dev/sda` and printed nothing more for over an hour. It then finished normally: 0 pass/verification/fdatasync errors, exit 0, script readback-sample 5/5.
- **Cause**: nwipe's default `verify = 1 (last pass)` reads the whole drive back after the write pass and prints nothing until it's done. Timings on 040: write 09:31 → 11:01, read-back 11:01 → 12:24. The `/proc/<pid>/io` progress check in `erase-partition.sh` watches `write_bytes`, which stays flat during the read-back, so it would also make the wipe look stuck. Watch `read_bytes` instead (comment updated in the script).
- **Not a cause**: plugging a keyboard back in coincided with seeing it finished; the log shows it had completed on its own at 12:24. The screen had most likely just blanked.
- **Applies to**: every `nwipe` run (plain HDD branch and NVMe Clear-tier fallback). Expect roughly double the write time in total.

### HDD passes SMART at opening diagnostics, fails it after the nwipe run
- **Symptom**: on 040/FR1586 (HP EliteOne 800 G1, HGST HTS725050A7E630 500 GB, 2026-10-19), Ubuntu showed a "disk may be failing" popup during the nwipe run. The next boot stopped at the HP BIOS with `1720-SMART Hard Drive detects imminent failure`, `Failing Drive: SATA0 (Dark Blue)`, `Failing Attribute: #B8`. The wipe itself had reported 0 errors and passed verification.
- **SMART, before vs. after** (`smartctl -H -A`):
  - Opening diagnostics: overall PASSED; 184 End-to-End_Error `100 / thresh 097`, raw 0.
  - After the wipe: overall **FAILED** ("Drive failure expected in less than 24 hours"); 184 `001 / thresh 097`, **FAILING_NOW**, raw 10354688. `smartctl` exit 24 (bits 3 + 4).
  - Unchanged: reallocated, pending and offline-uncorrectable sectors all 0, error log empty. The 32 GB SanDisk SSD in the same machine stayed PASSED (exit 0).
- **What 184 means**: the drive's own parity check on data moving through its internal buffer, between the SATA interface and the platters, found mismatches. It's a controller/cache fault rather than bad sectors, which is why the sector counts stay at 0. That fits the drive passing at opening diagnostics: the fault showed up under the hours of continuous I/O.
- **187's raw value was a packed field, not a count**: before the wipe it read `4294967296` (2³²). Afterwards it read `4305321984`, and the difference is exactly 10354688, the same as 184's new raw value. The low 32 bits count the same events; the high bits are something else. Read 187's low 32 bits on these HGST drives, not the whole number.
- **Why our workflow missed it**: SMART was only read at opening diagnostics, before the erase, and at closing diagnostics, after Windows is installed. Ubuntu's disk monitor and the BIOS caught it; nothing in our scripts looked in between. Fix: `erase-partition.sh` v16 runs `smartctl -H -A` after every erase and stops before the zap if the disk is failing.
- **Disposition**: don't install Windows on the disk or ship it. Even if the counter were spurious, every boot would show the 1720 warning to the recipient. The erase itself passed (full zero-fill, nwipe's full read-back and the script's 5-point sample all clean), but a failed drive leaving the building is normally destroyed rather than reused; Le Relais decides. The machine needs a replacement 2.5" SATA drive or goes to parts: the 32 GB SSD alone is below Windows 11's 64 GB minimum.

### `hdparm --security-erase-enhanced` fails erase-partition.sh's own verification on a real SATA SSD
- **Symptom**: on 002 (SATA SSD), `erase-partition.sh` v9's SATA-SSD branch ran `hdparm --security-erase-enhanced` to completion (`exit=0`), but the following `readback-sample` verification step then failed — non-zero data present at the offset-0% sample.
- **Cause**: per ATA spec, plain `SECURITY ERASE UNIT` is defined to write binary zeroes to user data areas; `ENHANCED SECURITY ERASE UNIT` writes a manufacturer-defined pattern instead, which is not guaranteed to be zero. `erase-partition.sh`'s `readback-sample` verification only checks sampled offsets against an all-zero reference (`cmp` against `/dev/zero`) — a design choice that was fine when the SATA-SSD branch used plain Secure Erase exclusively, but breaks the moment Enhanced is used on a drive whose vendor pattern isn't zero.
- **Confirmation**: re-running the identical drive (002) with the prior (v1-tagged) script — plain `--security-erase`, no Enhanced preference — passed verification cleanly at every sampled offset. Same drive, same verification method, only the erase variant changed.
- **Fix**: `erase-partition.sh` v10 reverts the SATA-SSD branch to plain `--security-erase` only; the Enhanced-preferring branch introduced in v9 is removed. See `methodology.md` §4.3 for the full reasoning, including why teaching the verification step to accept a non-zero pattern instead was considered and rejected (added complexity for a benefit — Enhanced's broader reallocated/spare-sector coverage — that isn't NIST-certified in the first place; see the same section).
- **Applies to**: any machine that would have hit the SATA-SSD branch between v9's introduction and v10's revert (2026-09-28, same day — narrow window, but worth checking `erase_method` in any affected machine's `summary.csv` row if that window is uncertain). Machines sanitized with v1–v8's plain `--security-erase`, or v10 onward, are unaffected.

## Windows install

### Windows Setup fails late in "Installing Windows" with a popup giving no detail — damaged `install.wim` on the USB stick
- **Symptom**: on 003/CIAD7415 (2026-09-30), Windows Setup failed twice, late in the file-copy stage. The second time it was at 78%, after the percentage had stalled for several minutes. The popup gave no error code and no detail. Setup had already partitioned the disk: the next attempt found a 200 MB System, a 16 MB MSR and a 238.3 GB partition where the erase had left only unallocated space. The second attempt was on a different USB port. At the failure, the stick was still listed in `diskpart` → `list disk`, and the target SSD's SMART data was clean (opening diagnostics).
- **Misleading log lines**: the last lines of `setuperr.log` were repeated `HWReqChk` errors ("failed to get / failed to retrieve settings"), from Setup's Windows 11 hardware-requirements checker failing to load its settings. They weren't the cause here: the damaged stick was.
- **Cause**: `sources\install.wim` on the stick didn't match the ISO's copy (SHA-256 mismatch, confirmed afterwards on the Rufus laptop). A failure at about the same percentage on both attempts fits a damaged file: Setup reaches the same damaged part of the image at the same point every time. It's unconfirmed how the file got damaged. A plausible cause is that the Rufus laptop kept going to sleep on its own while plugged in, which can interrupt the stick mid-write.
- **Fix**: rewrote the ISO to a different stick, confirmed the stick's `install.wim` matched the ISO's, and confirmed the ISO itself by downloading it twice and comparing hashes. The install then completed. `scripts/windows/verify-usb.ps1` now does the stick-vs-ISO check, and `toolkit-reference.md` ("Building each Rufus USB") runs it after every write, with sleep disabled on the Rufus laptop first.
- **Confound**: the attempt that worked also had the network cable unplugged. The old stick's hash mismatch makes the stick the cause. Installing offline stays in the walkthrough as a cheap precaution, not a proven fix.
- **Reading the logs at the failure popup (for next time)**: leave the popup open and press Shift+F10.
  - Check the stick is still connected with `diskpart`, then `list disk`.
  - Find the log with `dir X:\setuperr.log /s /b`, and again with `C:` in place of `X:`. `where` doesn't exist in Setup's environment.
  - Open it with `notepad <path>`, then Ctrl+End. `setupact.log` in the same folder has more detail.
  - The command window uses the keyboard layout picked on Setup's first screen. `wpeutil SetKeyboardLayout` reported success but didn't change the layout in the open window. So pick Français (Suisse) on the first screen.
- **Applies to**: any machine. This is a problem with the stick, not the machine. Treat every Windows stick written before `verify-usb.ps1` existed as unverified until it's been checked.

## Windows Update stage

### Files created under `C:\ProgramData\Refurb` don't inherit the folder's ACL — Access Denied reading them back, even from a fully elevated Administrator session
- **Symptom**: `Get-Content` on `update-log.txt` or `update-status.txt`, and running `check-update-status.ps1` from its `C:\ProgramData\Refurb` copy, all fail with "L'accès au chemin d'accès ... est refusé" (`UnauthorizedAccessException` / `PermissionDenied`) — confirmed from a console where `([Security.Principal.WindowsPrincipal][Security.Principal.WindowsIdentity]::GetCurrent()).IsInRole([Security.Principal.WindowsBuiltInRole]::Administrator)` returns `True`, so this isn't a missing-elevation mistake. `icacls` on the affected files shows either zero ACEs (file readable enough to list, but empty — deny-all) or, for a file the current account doesn't own, "Accès refusé" on the `icacls` query itself.
- **Diagnosis trail** (2026-09-29, first real-hardware run of the v4 COM-API rewrite):
  1. Confirmed elevation via the `WindowsPrincipal` check above — ruled out a non-elevated console before looking any further.
  2. `icacls C:\ProgramData\Refurb` (the folder itself) correctly shows the two ACEs `register-update-loop.ps1` sets (`BUILTIN\Administrateurs:(OI)(CI)(F)`, `AUTORITE NT\Système:(OI)(CI)(F)`) — the folder's own ACL is exactly as intended.
  3. Checked four files, each created by a different mechanism: `update-log.txt` (`Add-Content`), `update-pass-count.txt` (`Set-Content`), `update-status.txt` (write-to-`.tmp` then `Move-Item -Force` over the target), and `check-update-status.ps1` (`Copy-Item`, from `register-update-loop.ps1`). All four show the same empty-DACL symptom — this rules out any one cmdlet or write pattern as the cause. Something about files created inside this specific locked-down folder isn't inheriting its `(OI)(CI)` ACEs, independent of how they're written.
  4. `takeown /F` on an affected file succeeds (the elevated account has `SeTakeOwnershipPrivilege`, which can seize ownership of an object regardless of its current DACL) and changes only the owner, not the DACL — re-running `icacls` afterward still showed zero ACEs. Confirms the DACL genuinely has no entries, not just entries this account can't read.
- **Cause**: not confirmed. Newly created child objects should inherit a parent's `(OI)(CI)` ACEs automatically; that didn't happen here for any of the four write mechanisms tested. Leading but **unverified** guess: a security baseline/GPO on these machines forcing new objects not to inherit parent DACLs — not checked against actual policy, so treat as plausible, not settled (same standard as the nwipe `SIGUSR1` note above). Machine 003 weighs against it: a baseline applied to every fresh install should have hit 003 too, and it didn't (see **Applies to**). That points to something specific to the first machine or its state, still unidentified.
- **What still worked despite this**: the `RefurbWindowsUpdate` scheduled task itself, running as SYSTEM, wrote correct state throughout (real driver/update results ended up in `update-log.txt`) — SYSTEM's own access to files it creates isn't gated the same way. The bug only blocks a *human* reading that state back afterward, which is exactly the "Windows Update stage — full walkthrough" step 3–4 verification in `toolkit-reference.md`.
- **Fix (workaround, confirmed working once)**: one recursive sweep of the whole folder, run **only when** `check-update-status.ps1` (itself one of the broken files) or a manual read fails with Access Denied or reports `NO STATUS FILE`; then re-run the check. Once a machine has needed it, expect to need it again at later checks. Why: the loop keeps creating new files after the first sweep (`update-status.txt` is replaced via write-to-`.tmp` + `Move-Item` on every state change; a new transcript per pass), and it isn't confirmed that those inherit correctly afterward. If they don't, `check-update-status.ps1` misreports `NO STATUS FILE`. The sweep is idempotent, so repeating it is harmless:
  ```
  takeown /F C:\ProgramData\Refurb /R /D O
  icacls C:\ProgramData\Refurb /grant:r "*S-1-5-32-544:(OI)(CI)F" "*S-1-5-18:(OI)(CI)F" /T /Q
  ```
  `toolkit-reference.md`'s walkthrough includes this as a conditional step. If this turns out to recur, a real fix belongs in `register-update-loop.ps1`/`update-loop.ps1` — explicitly re-applying ACLs to each file after creating it, rather than relying on inheritance that's demonstrably not propagating here — but that means cutting a new tag and re-verifying checksums batch-wide, so it hasn't been done yet.
- **Applies to**: not every machine. Confirmed on one real machine (the first v4 run), across four file-creation mechanisms on that machine. **Not** seen on 003 (ThinkCentre M900z), which ran the same `register-update-loop.ps1`/`update-loop.ps1` (unchanged since v4): `check-update-status.ps1` and the file reads worked with neither `takeown` nor `icacls`. So identical scripts don't always trigger it. If it comes back on another machine, record which machine it was and its state (e.g. whether `register-update-loop.ps1` was re-run over an existing folder) here, to narrow down the cause.
